# 1. 文档作用

PRD 解决“做什么、为什么做、做到什么程度”。

工程文档解决：

- 在现有仓库中改哪些文件；
- 新增哪些目录、服务、数据表和接口；
- 前后端怎样连接；
- 旧数据怎样兼容；
- 功能怎样测试、发布和回滚；
- 每项工作如何拆成可以执行的开发任务。

执行层级统一为：

```text
产品 PRD
  → 组件 PRD
    → 组件工程设计
      → 工程任务
        → 代码提交
          → 测试与验收
```

# 2. 总体工程决策

1. 保留现有静态 HTML、共享 JavaScript 和五个剧本页面，不整体迁移框架。
2. 新增一个轻量 Node.js API 服务，承载 AI 代理、事件采集、管理员登录、反馈和许愿池。
3. MVP 使用 SQLite 持久化，启用 WAL；数据访问通过 Repository 层隔离，后续可切换 MySQL/PostgreSQL。
4. 管理员后台继续使用原生 HTML、CSS、JavaScript，避免引入第二套前端框架。
5. 学生和教师保持免注册，使用随机匿名 ID；管理员使用正式服务端账号。
6. 学习进度继续保存在本机；只有经过白名单定义的产品事件、反馈、愿望和 AI 运行记录上传服务端。
7. AI 输出必须经过结构校验；失败、超时或格式错误时自动降级到规则版。
8. 事件采集失败不能阻断剧情、答题、导学或复盘。
9. 所有新增能力通过独立适配层接入，避免把五个剧本分别重写。
10. 比赛前优先完成可运行闭环，复杂统计、多租户、班级管理继续留在 P2。

# 5. 工程状态规则

- `待开发`：工程设计完成，尚未开始代码。
- `开发中`：已有对应分支或提交。
- `联调中`：前后端接口已接通。
- `待验收`：代码完成，等待按文档验收。
- `已上线`：生产环境验证通过。
- `已回滚`：上线后撤回，保留问题记录。

每个工程任务完成必须同时满足：

1. 代码已提交；
2. 自动测试通过；
3. 手工验收通过；
4. 文档状态已同步；
5. 没有新增未说明的数据采集；
6. 有明确回滚路径。

# 6. 执行控制规则

工程任务的拆分与依赖以 `ENG-01` 为准，实际每日排期、优先级、砍项顺序、冻结时间和放行门槛以 `ENG-06` 为准。

执行原则：

1. 先完成参赛核心闭环，再建设后台增强；
2. 每天结束必须保留可运行版本；
3. 单个外部服务问题阻塞超过两小时，启用降级方案；
4. 8 月 9 日冻结教师导学卡和学生复盘卡结构；
5. 8 月 12 日完成全功能冻结；
6. 8 月 13 日只处理阻断问题和提交材料。

# 7. 变更纪律

工程实现发现 PRD 不可执行时：

1. 先记录冲突；
2. 回写对应组件 PRD；
3. 同步总 PRD；
4. 再修改工程设计；
5. 最后进入代码。

不得通过代码默认值偷偷改变产品规则。
