# 1. 文档层级

本项目采用四层产品结构：

```text
产品
  └─ 组件
       └─ 模块
            └─ 功能
```

## 1.1 产品

产品是用户最终使用和感知的完整解决方案。

本项目的产品是：

> 时空剧场 AI 导学版

它解决三件事：

1. 老师怎样把现有互动历史剧本拿进课堂；
2. 学生完成学习后，怎样知道自己哪里需要补；
3. 产品团队怎样看见真实使用、处理反馈并决定后续优先开发什么。

## 1.2 组件

组件是一组相对独立、边界清楚、可以持续演进的业务能力。

组件通常具备：

- 独立目标；
- 明确用户或调用方；
- 自己的数据和规则；
- 可被多个页面或流程复用；
- 可以单独规划版本和验收。

例如：

- 卡牌系统是组件；
- 账号会员系统是组件；
- AI 教学助手是组件；
- 学习数据与评估是组件；
- 用户互动与许愿池是组件。

## 1.3 模块

模块是组件内部面向某类用户、场景或职责拆出的子能力。

模块通常：

- 依附于一个组件；
- 服务一类角色或一段流程；
- 使用组件的公共数据和规则；
- 可以独立设计页面、流程和验收项。

例如账号会员系统包含：

- 学生账号模块；
- 教师账号模块；
- 管理员账号模块。

用户互动与许愿池系统包含：

- 用户互动事件模块；
- 管理员互动看板模块；
- 用户反馈模块；
- 许愿池模块；
- 愿望治理与产品路线图模块。

## 1.4 功能

功能是用户可以直接操作或系统可以直接执行的最小需求单元。

例如：

```text
账号会员系统
  └─ 教师账号模块
       ├─ 进入教师导学入口
       ├─ 保存最近使用剧本
       └─ 查看已生成导学卡
```

```text
用户互动与许愿池系统
  └─ 许愿池模块
       ├─ 提交剧本愿望
       ├─ 提交功能愿望
       ├─ 查看愿望状态
       └─ 点亮公开愿望
```

# 2. 判断一个能力是组件还是模块

使用以下五个问题判断：

| 判断问题 | 更像组件 | 更像模块 |
|---|---|---|
| 能否被多个场景复用 | 是 | 通常只服务一个场景 |
| 是否拥有独立数据模型 | 通常有 | 多数复用组件数据 |
| 是否可以单独规划版本 | 可以 | 跟随组件版本 |
| 是否包含多个角色或流程 | 通常包含 | 通常聚焦一个角色或流程 |
| 移除后是否影响多处产品能力 | 会 | 主要影响局部流程 |

判断示例：

- “卡牌获取、使用、图鉴、练习”共同组成卡牌系统，因此卡牌系统是组件。
- “学生使用游客身份保存本机进度”只服务学生身份，因此学生账号是账号会员系统中的模块。
- “生成导学卡”服务教师课前场景，因此教师导学卡是 AI 教学助手组件中的模块。
- “用户互动事件、管理员看板、反馈、许愿和路线图”拥有独立数据、权限和流程，因此共同组成用户互动与许愿池组件。
- “提交剧本愿望”只服务许愿流程，因此是许愿池模块中的功能。

# 6. 关键边界

## 管理员“查看所有互动”的定义

指管理员可以查看事件目录中明确登记的产品行为，例如：

- 页面进入；
- 剧本开始和完成；
- 幕次到达；
- 关键选择；
- 证据和卡牌互动；
- 答题结果；
- 导学卡和复盘卡生成状态；
- 用户主动提交的反馈和愿望。

不包含：

- 密码；
- 屏幕录像；
- 键盘监听；
- 与产品无关的浏览记录；
- 广告画像；
- 未经用户主动提交的私人聊天。

## 本机学习档案与云端事件

- 本机学习档案用于学生续玩和个人复盘；
- 云端事件用于产品改进和管理员匿名分析；
- 本期不提供跨设备学习同步；
- 学生和教师不需要注册；
- 管理员必须登录。

# 7. 版本规则

文档状态统一使用：

- `草案`：方向正在讨论；
- `已确认`：可以进入设计或开发；
- `开发中`：需求已经冻结；
- `已上线`：功能已进入生产环境；
- `已废弃`：保留历史，停止执行。

需求优先级统一使用：

- `P0`：本次比赛 MVP 必须完成；
- `P1`：完成后明显提升体验；
- `P2`：比赛后建设。

范围发生变化时，按以下顺序更新：

1. 母文档；
2. 总 PRD；
3. 对应组件 PRD；
4. 组件内模块；
5. 开发任务与验收项。
